# 테스트 작성 가이드 — AI 개발 멘토

**작성일:** 2026-09-11 · **작성자:** 오승연

이 문서는 테스트 코드를 작성할 때 (1) 어떤 로직을 검증 대상으로 우선 선정할지, (2) AI로 테스트 코드를 생성(바이브코딩)할 때 엔지니어링 관점에서 무엇을 추가로 점검해야 할지를 정리한 공통 지침이다. 특정 기능 단위가 아니라 프로젝트 전반의 테스트 작성에 적용한다.

## 1. 검증 대상 선정 기준

새로운 로직이 생기거나 기존 코드에 테스트를 추가할 때, 아래 기준으로 우선순위를 매긴다.

- **순수 함수인가.** 입력이 같으면 항상 같은 출력이 나오고 부수효과(네트워크·DB·전역 상태 변경)가 없는 함수일수록 테스트 작성이 쉽고 가치가 높다. 이런 함수부터 우선한다.
- **깨졌을 때 파급력이 큰가.** 예를 들어 파싱 로직이 깨지면 그 위의 기능 전체가 망가지고, 방어 로직(예: 프롬프트 인젝션 방어 문구)은 리팩토링 중 실수로 지워져도 겉으로 티가 나지 않는다. 이렇게 "조용히 깨질 수 있는" 로직을 우선순위 위로 둔다.
- **외부 의존성이 적은가.** 실제 API 호출·DB·UI 렌더링이 얽힌 코드는 단위테스트보다 통합테스트/E2E 영역에 가깝다. 이런 코드는 단위테스트 범위에서 제외하고 별도로 다룬다.

로직이 거의 없는 상수·데이터 파일(옵션 목록 등)은 위 기준에서 다 낮은 점수를 받으므로 우선순위 최하로 두거나, 시간이 부족하면 생략한다.

## 2. 바이브코딩 시 엔지니어링 체크리스트

핵심 로직 파악과 엣지케이스 도출 외에, AI가 테스트 코드를 대신 작성해줄 때 특히 놓치기 쉬운 부분이다.

### 2.1 테스트가 가짜로 통과하는 건 아닌지 확인한다

AI에게 테스트 작성을 맡기면, 구현 코드를 그대로 베껴서 항상 통과만 하는 테스트(tautological test)를 만들 위험이 있다. 테스트를 작성한 뒤에는 검증 대상 로직을 일부러 하나 깨뜨려보고(예: 조건문을 반대로 바꿔보기) 테스트가 실제로 실패로 바뀌는지 확인한다. 실패로 바뀌지 않으면 그 테스트는 아무것도 검증하지 않는 것이다.

### 2.2 구현이 아니라 동작을 검증한다

"내부적으로 이 변수를 이렇게 쓴다"가 아니라 "이 입력을 주면 이 출력이 나와야 한다"만 확인한다. 내부 구현 디테일에 테스트가 묶이면, 동작은 그대로인데 리팩토링만 해도 테스트가 깨져서 오히려 리팩토링을 방해하게 된다.

### 2.3 결정론적으로 만든다 (flaky 테스트 방지)

실제 네트워크·타이머·난수 등 외부 요인에 결과가 좌우되는 테스트는 피한다. 예를 들어 스트림을 다루는 로직은 실제 fetch 대신, 테스트 안에서 청크 크기·타이밍을 직접 통제한 mock 스트림을 사용한다. 그래야 환경에 따라 결과가 달라지는 일이 없다.

### 2.4 테스트 간 격리를 지킨다

전역 상태(스토어 등)를 다루는 테스트는 각 테스트 시작 전에 상태를 초기화한다. 그러지 않으면 테스트 실행 순서에 따라 결과가 달라지는 순서 의존적 버그가 생긴다.

### 2.5 하나의 테스트는 하나의 개념만 검증한다

한 테스트에 여러 assert를 몰아넣어 여러 조건을 한꺼번에 확인하면, 실패했을 때 원인을 특정하기 어렵다. 테스트 이름을 "~일 때 ~해야 한다" 형태로 짧게 쪼개면 테스트 자체가 스펙 문서 역할을 한다.

### 2.6 커버리지는 목표가 아니라 신호로 다룬다

"몇 퍼센트를 커버했는가"보다 "회귀 위험이 큰 로직을 실제로 잡았는가"를 기준으로 삼는다. 100% 커버리지를 노리다 로직이 없는 상수 파일까지 테스트를 늘리는 것은 시간 대비 가치가 낮다.

## 3. 향후 방향: QA 자동화 이관

QA 자동화(단위테스트 범위를 넘어서는 검증)도 셋업할 계획이지만, 아직 어떤 범위를 AI에게 맡기고 어떤 범위를 직접 판단할지 기준이 서지 않은 단계다. 그래서 지금은 검증 과정에 직접 많이 관여하며 필요한 자동화를 하나씩 셋업하고, AI가 낸 결과에 대한 신뢰가 쌓이는 만큼 판단을 점진적으로 이관하는 방식으로 자동화 범위를 넓혀간다. 즉 처음부터 큰 범위를 위임하지 않고, 검증된 부분부터 단계적으로 맡긴다.

## 4. 조사 예정: 바이브코딩에서 테스트 코드 작성 시점

테스트를 코드 작성 흐름의 어느 시점에 넣을지는 아직 결론이 없어 자료 조사가 필요한 열린 질문으로 남겨둔다.

- **강사님 사례**: 서비스 핵심 부분의 테스트 케이스를 먼저 엑셀에 나열(이 역시 AI로 생성하되, 본인이 생각하는 핵심과 일치하는지 검토는 필수)하고, 그걸 바탕으로 단위 테스트를 작성하도록 지시하는 방식. 개인적으로는 TDD처럼 처음부터 테스트를 앞세우기보다, 전체 작업의 약 70% 시점에 테스트를 추가하는 편이라고 함 — 작업 속도 저하가 이유로 보임.
- **본인 경험**: 직접 코드를 짤 때는 TDD가 유의미했으나, 최근에는 모델 성능이 좋아지기도 했고, 초반에 짠 테스트 코드가 이후 수정을 거듭하면서 오히려 병목이 되어 결국 테스트 파일을 삭제한 경험이 있음.

바이브코딩(AI에게 구현을 상당 부분 맡기는 방식)에서 테스트를 언제 도입하는 게 적절한지 — TDD처럼 선행할지, 일정 진행 후 추가할지, 혹은 그 중간 지점이 있는지 — 관련 자료를 찾아보고, 이 프로젝트의 지침에 반영할지 판단한다.

## 5. 스코프 결정: 통합테스트는 백로그로 보류

온보딩→실습 생성→학습으로 이어지는 파이프라인 전체가 맞물려 동작하는지 확인하는 통합테스트는, 지금 시점에는 백로그로만 남겨두고 진행하지 않는다.

- 확정된 MVP 스코프(CI/CD 코드체크·핵심 단위 테스트·엣지케이스 테스트·재현성+rubric·프롬프트 인젝션 방어·실패처리)에 통합테스트가 별도 항목으로 포함되어 있지 않다.
- LLM이 낀 파이프라인의 통합테스트는 mock 설계·결정론성 확보 비용이 단위테스트보다 훨씬 크다. 남은 시간을 여기 쓰면 정작 필수 항목인 핵심 단위 테스트 커버리지가 부족해질 위험이 있다.
- 여유가 생기면 `/api/practice` 같은 핵심 경로에 대해 happy-path 하나 정도의 가벼운 스모크성 통합테스트만 추가하는 선에서 그친다.
