# AI 맞춤 실습 생성기 — 1일차 제출 원페이저

**작성일:** 2026-08-19 · **트랙:** 개발(프론트엔드) · **작성자:** 오승연

---

## 프로젝트 개요

배운 개념을 실습에 적용 못하고 AI에게 어떻게 물어야 할지 몰라 이탈하는 학습자를 위해, 프롬프트 작성 없이 구조화된 선택 UI로 개인화된 실습을 생성하고 같은 화면에서 실행·피드백까지 받는 AI 학습 서비스다.

- 이를 해결하는 프론트엔드 화면 하나를 5일 안에 만든다

---

## 프로젝트 세부 내용

### 1. 목표 (Objective)

- AI 기능이 들어간 프로덕트 화면 하나를 5일 안에 완성도 있게 만든다
- 학습자가 개념을 선택하면 그 자리에서 개인화된 실습을 받는다
- 같은 화면에서 코드를 실행하고 피드백까지 받는 루프를 증명한다
- 부트캠프 평가 기준(문제정의·동작완성도·성능지표·안정성·재현성·문서회고)을 모두 충족한다
- 동시에 EdTech 프론트엔드 채용 포트폴리오로 쓸 수 있는 수준으로 만든다

### 2. 배경 (Background)

- 멘토링 중 학습자 4~5명에게 AI 활용 학습법(4단계: 개념파악→기본실습→심화탐구→마무리)을 가이드하고, Gemini Gems에 지침을 복사해 활용할 수 있도록 안내함
- 1~2명이 시도했고 "본인 수준에 맞는 실습을 만들 수 있었다"는 효과를 직접 보고함
- 그런데도 2주 안에 이탈함
- 이탈 원인은 AI 성능이 아니라: (1) 어떻게 물어봐야 할지 모름(프롬프트 장벽), (2) 실습 지시를 받아도 에디터로 옮겨가는 절차가 번거로움(전환 비용)

### 3. 가설과 검증 전략 (Hypothesis & Validation Strategy)

**가설:** 프롬프트 작성을 구조화된 선택 UI로 대체하고, 코드 실행을 같은 화면 안에 두면(에디터 이동 제거), 학습자가 개념→실습 전환을 더 쉽게 지속할 수 있다.

**검증 전략:** 5일 안에 실사용자 행동 데이터(실제 이탈률 감소 등)를 구하는 건 불가능하므로, 기술적·설계적 대리 지표로 검증한다.
- **생성 품질 자가 채점**: 개념×PCM-L 3단계 조합 샘플(예: 5개념×3단계=15건)에 대해 체크리스트(정답을 바로 안 주는가 / 완료 기준이 명확한가 / 코드가 실제로 실행되는가)로 직접 채점해 통과율을 낸다
- **전환 비용 정량 비교**: 기존 방식(챗봇에 직접 프롬프트 작성 + 외부 에디터 이동)과 이번 방식(구조화 선택 + 같은 화면 실행)의 필요 클릭 수·화면 전환 횟수를 설계 비교표로 제시한다
- Lighthouse 성능·접근성 점수, 번들 크기, 첫 상호작용까지의 체감 시간을 스트리밍 UI 적용 전후로 비교
- 이상 입력(빈 값, 매우 긴 텍스트, API 실패)에서도 로딩/에러/빈화면 상태가 깨지지 않는지 확인
- 동일 입력에 대한 재현성(같은 개념·같은 단계 입력 시 결과 일관성) 점검

**한계:** 이번 검증은 전부 기술·설계 차원이며, "실제 학습자의 지속률이 올랐는가"는 이번 스코프에서 증명하지 못한다. 다음 단계(회고/미래 비전)에서 명시할 한계로 남긴다.

### 4. 원칙 (Guiding Principle)

**가장 중요한 주요 원칙 (중요도 '상')**
- 사용자는 어떤 경우에도 원시 프롬프트를 직접 작성하지 않는다. 모든 입력은 구조화된 선택(개념 선택기·상태 선택기·상황 칩·선택적 한 줄 입력)으로만 이루어진다.

**중요도가 보통인 주요 원칙 (중요도 '중')**
- 코드 실행은 화면을 벗어나지 않는다 — 실습 생성과 실행이 같은 화면 안에서 이어져야 하며, 이게 기존 챗봇 방식과의 근본적 차이다.
- AI 피드백은 정답을 바로 주지 않고, 관찰 결과를 해석해주고 다음 질문을 던지는 방식으로만 준다(PCM-L 멘토 질문 원칙).

**가장 덜 중요한 주요 원칙 (중요도 '하')**
- 에디터 컴포넌트는 실행 엔진과 분리해 구현한다 — 지금은 Sandpack 기본 에디터를 쓰지만, 나중에 LXP 학습 플랫폼 타겟팅에 맞춰 Monaco로 교체할 수 있게 인터페이스만 독립적으로 둔다.
- 실습 콘텐츠의 교육적 품질(예제 선택, 강조점)에는 저자의 주관을 반영할 여지를 남긴다 — 1차 생성 후 직접 검수하며 프롬프트 템플릿을 조정한다.

### 5. KPI (Key Performance Indicator)

| 지표 | 목표 | 대응하는 평가 기준 |
|---|---|---|
| 원시 프롬프트 작성 UI 존재 여부 | 0건 (완전 제거) | 문제 정의 |
| 전체 루프(입력→생성→실행→피드백) 동작 시나리오 | 여러 개념·난이도 조합에서 100% 동작 | 동작·완성도 |
| Lighthouse 성능/접근성 점수 | 개선 전후 비교, 접근성 90점 이상 | 성능 지표 |
| 번들 크기 / 첫 상호작용 체감 시간 | 개선 전후 수치 제시 | 성능 지표 |
| UI 상태 커버리지 | 로딩·스트리밍·에러·빈화면·완료 5개 상태 전부 구현 | 안정성 |
| 이상 입력 방어 | 빈 입력·API 실패·긴 텍스트 등에서 크래시 없음 | 안정성 |
| 재현성 | 동일 입력 반복 시 결과 일관성 확인 | 재현성 |
| 문서화 | 컴포넌트 문서 + 대안 비교 + 한계 기술 | 문서·회고 |
