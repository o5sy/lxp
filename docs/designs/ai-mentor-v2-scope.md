# 스코프 결정 기록 — AI 개발 멘토 2차 프로젝트

**작성일:** 2026-09-10 · **작성자:** 오승연

이 문서는 커리어캠프 2차 개인 프로젝트(1차 [AI 개발 멘토](ai-adaptive-practice-generator.md)의 후속작)를 위해 브레인스토밍 → 타겟 채용공고 분석 → 우선순위 산정 → 스코프 확정까지 진행한 의사결정 과정과 그 결과를 기록한다. 다음 세션에서 이 문서만 보고 바로 구현을 이어갈 수 있도록, **결정된 내용과 그렇게 결정한 기준·이유**를 함께 남긴다.

## 1. 배경

1차 프로젝트 회고(KPT)에서 나온 아쉬운 점:

- 실패 처리·재시도·동시성 등 실제 문제 해결에 가까운 고민 부족
- 프롬프트 인젝션 검토를 백로그에만 적어두고 실제로 실행하지 않음
- 테스트 코드 전무
- `/investigate`·`/security-review`·`/cso` 미사용
- 커밋 메시지가 실제 diff보다 축소 표현된 사건이 마무리 단계에야 발견됨

2차 프로젝트의 목적:

- **1순위**: 취업 포트폴리오로 쓸 수준까지 보완
- **2순위**: 실제로 좋은 서비스로 만들고 싶다는 개인적 동기

두 목표는 서로 독립적이지 않다 — 아래 §3의 "견고성 → 효과성" 순서가 포트폴리오 목적(타겟 공고 요건이 견고성과 크게 겹침, §4 참고)과 실제 서비스 목적(효과성 검증)을 함께 충족시키는 구조로 확인됐다.

## 2. 문제 재정의

1차의 핵심 문제는 "개념→코드 전환 실패"였다. 2차에서도 이 문제가 여전히 유효한지 재점검했다:

- 1차는 Full Vision `[1]~[4]`(입력→생성→실행→1회 피드백)만 구현했고, `[5] 반복 루프`·`[6] 회고 기록`은 "미래 비전"으로 미뤄졌다 — 전환 실패의 본질이 "1번 만에 성공"이 아니라 "막혔을 때 다시 시도하며 배우는 과정"이라면, 반복 루프 없이 이 문제를 풀었다고 보기엔 부족할 수 있다.
- 1차 검증은 전부 기술적 대리 지표였고, "실제 학습자의 지속률이 올랐는가"는 이번에도 증명되지 않은 채로 남을 수 있다.

이 재점검 과정에서 "품질"이라는 개념 자체가 모호하다는 문제가 드러나 두 단계로 재정의했다:

1. **품질 vs 사용성** (강사님 기준): 품질 = 동작이 된다/안 된다, 테스트 케이스로 판정 가능한 것. 사용성 = 편리함, 사람마다 다르게 느끼는 것.
2. **품질 내부의 효과성 vs 견고성**: 효과성 = 사용자의 진짜 문제를 해결하는가·의도에 부합하는가 (답을 얻으려면 실사용자가 필요). 견고성 = 이상 입력·예외 상황에서도 안 깨지는가·결과 형식이 일관되는가 (기술 점검으로 충분).

업계 리서치로 뒷받침한 근거:

- LLM 응답 평가는 rubric 기반 pairwise/단일채점이 표준이며, 신뢰성(재현성)·편향 통제(생성자·평가자에 같은 모델 안 쓰기)가 핵심 축이다.
- AI 공동작성 코드는 로직 결함이 75% 늘고 OWASP Top-10 미통과율이 45%에 달한다는 실측이 있다 — "일단 돌아간다"와 "제대로 동작한다" 사이 간극이 vibe coding의 핵심 리스크.
- Spec-driven development에서 말하는 "Hooks"(자동화된 가드레일)가 "지시"보다 신뢰할 수 있는 프로세스 제어 수단이라는 게 업계 공통 방향.

## 3. 우선순위 판단 기준 (적용 순서, 최신 확정본)

1. **선행 관계(의존성) 우선** — 다른 작업의 전제 조건이 되는 항목은 중요도와 무관하게 먼저.
2. **기능(Product)은 "동작 여부"까지만 우선순위 대상** — 이미 동작하는 기능을 더 다듬는 작업은 후순위로 내린다.
3. **기능이 동작 수준에 도달하면, 최소 견고성 확보 트랙부터** — 데이터 확보·효과성 검증 트랙은 병렬이 아니라 그 다음 순서(캠프 기간 내에서 순차로, §7 참고).
4. **엔지니어링 트랙 내부에서는 "코어 & 저변화율" 우선** — 기능이 나중에 바뀌어도 안 흔들리는 구조적 작업을 우선하고, 특정 기능 디테일에 강하게 묶인 지엽적 개선은 후순위.
5. **예방적 개선보다 "이미 드러난 문제" 우선** — 아직 증상이 안 나타난 예방적 시스템화는 메모로만 대기, 실제 문제가 관찰된 뒤 적용.

그 외 참고할 만한 교차 신호:

- 랭디 우대사항: 웹 성능 측정·개선, 코드리뷰+테스트 코드 품질관리, 런타임 스키마 검증/타입 안정성 — 엘리스 밖에서도 유효성 뒷받침
- 호랑에듀 우대사항: 사용자 테스트·피드백 기반 제품개선 사이클 — 효과성 트랙(§7에서 후순위로 미룬 항목)의 근거
- 취팡: "구체적인 세부 지시가 있어야 업무를 시작할 수 있는 분은 안 맞음" — auto mode가 지시 없이도 프로세스로 품질을 유지해야 한다는 이번 스코프의 문제의식과 결이 같음

## 6. 최종 확정 스코프

| 항목 | 결정 근거 |
|---|---|
| CI/CD 코드체크(lint/tsc) | 셋업 비용 거의 없이 이후 모든 작업의 안전망. **LLM 리뷰 단계는 이번 스코프에서 제외** — 아직 필요성을 못 느낌, 최소 버전(lint/tsc)만 먼저 |
| 핵심 파싱/검증 로직 단위 테스트 | 엘리스 우대사항(Jest/RTL/Cypress)에 정확히 대응 |
| 이상 입력 엣지케이스 테스트 케이스화 (형식 방어 + 개념 범위 판별) | 1차에서 실제로 드러난 갭("예상 시나리오 벗어나면 동작 모름"). 범위를 형식적 이상 입력(빈 값·특수문자)뿐 아니라 **"코드 실습으로 옮길 수 없는 개념"까지 넓힘** — 실제로 팀원이 "하네스 엔지니어링"을 입력했을 때 무관한 React 코드가 생성된 관찰 사례가 있어, 개념이 코드 실습에 부적합하면 억지로 생성하지 않고 이유를 설명하며 재입력을 유도하도록 함 |
| 재현성 검증 + LLM 평가 기준(rubric) 확장 | 사실상 한 작업 — rubric을 세우는 것 자체가 재현성 있게 품질을 정의하는 일. 별도 judge 모델 없이 프롬프트 rubric + 몇 차례 테스트로 보정 |
| 프롬프트 인젝션 방어 | 이미 배포돼 누구나 접근 가능한 상태라 실제 리스크 존재 |
| LLM 호출 rate limit | 무료 API 사용 시 실제로 발생하는 문제("몇 번 요청 시 사용 불가")의 직접 대응 |
| 실패 처리·재시도 | 1차에서 실제로 드러난 갭 |
| 데이터/세션 영속성(최소 localStorage) | 단독으로는 우선순위가 높지 않지만, **사용 로그 계측(이탈률/완수율)의 선행 작업**으로 필요 — 영속성 없이는 새로고침이 실제 이탈과 구분 안 돼 지표 자체가 오염됨 |
| YAGNI · SRP(단일 책임 원칙) | 구현 항목이 아니라 코드 작성 시 판단 기준(지침)으로만 적용. 코드 리뷰하며 발견되는 것들을 지침에 추가, 쌓이면 관련 스킬 탐색 |
| 전역 상태 이중소유 금지 | 유지(Sandpack 컨텍스트 한정 원칙, 범용 규칙 아님) |

## 7. 제외/보류 항목과 이유

| 항목 | 보류 이유 |
|---|---|
| 자동 PR 리뷰 시스템("코드래빗 흙수저 버전") | 여러 세션이 병렬로 작업 후 서로 리뷰하는 구조는 매력적이나, LLM 리뷰 단계 자체의 필요성을 아직 못 느낌. CI/CD 최소 버전(lint/tsc)이 먼저 자리잡은 뒤 확장 여부 재검토 |
| 기획/제품 카테고리 전체(맞춤형 실습 디테일, 점검 사이클 고도화) | 실사용자 데이터 확보 후 판단 |
| 사용자 검증 카테고리 전체(설문, 실사용 테스트, 사용 로그 계측) | §3 기준 ③에 따라 견고성 확보 트랙 다음 순서. 캠프 기간 내 진행: 최소 견고성 확보 → 설문/데이터 수집 → 효과성 테스트 순으로 |
| `/security-review`, `/cso` 스킬 실행 | 필요하나 우선순위 낮음, 스코프 확정 직후 한 번 실행 |
| `/investigate` 활용 | 필수 아님, 버그 수정 라운드 시작 시 쓰라는 메모 정도 |
| 작업 로그·의사결정 자동 기록 | 이번 프로젝트 주제와 직접 관련은 없음, 개인 습관으로 별도 셋업 고려 |
| 개념 적합성 1단계 사전 판별을 로컬 모델로 전환 | 현재는 1단계에서 화이트리스트 미매치 개념을 Gemini 경량 모델(`gemini-flash-lite-latest`)로 조회해 판별한다. 호출 비용·지연을 더 줄이려면 이 판별만 별도 로컬 모델(예: 소형 분류기)로 옮기는 방향이 낫다고 보나, 이번 스프린트 범위 밖이라 보류 |
| OfflineToast 정밀 테스트 + router.push 오프라인 감지 개선 | `useOnlineStatus`/`OfflineToast`는 헤드리스 브라우저에서 `online`/`offline` 이벤트를 직접 디스패치해 뜨고 사라지는 것만 확인했고, 실제 기기에서의 다양한 네트워크 전환 시나리오(느린 3G, 와이파이↔셀룰러 전환 등)는 아직 검증 안 됨. 또한 "실습 생성하기" 버튼을 누르는 시점에는 아직 온라인이었는데 그 직후(예: router.push 진행 중) 네트워크가 끊기는 레이스는 지금 `navigator.onLine` 클릭 시점 체크만으로는 못 잡는다 — `router.push()`의 RSC 페이로드 요청 자체에 AbortController/타임아웃을 걸어 이 구간도 감지하는 방향을 검토할 것. 발표 준비(자료·리허설)로 시간이 없어 보류 |

## 8. 최소 MVP (스코프를 한 번 더 좁힌다면)

**핵심 6개** (뺄 수 없음):

1. CI/CD 코드체크(lint/tsc)
2. 핵심 단위 테스트
3. 이상 입력 엣지케이스 테스트 (형식 방어 + 코드 실습 부적합 개념 판별)
4. 재현성 + LLM 평가 rubric
5. 프롬프트 인젝션 방어
6. 실패 처리·재시도

**흡수/보류 검토**:

- rate limit → 정교한 rate limiter 대신, 실패 시 에러 메시지 처리(6번)로 축소 가능
- 데이터/세션 영속성 → 로그 계측 자체가 후순위 단계이므로, 지금 MVP 단계에선 보류하고 효과성 테스트 착수 시점에 다시 꺼내도 됨

## 9. 무료 API 쿼터 제약 대응

무료 티어(Gemini) 호출 제한 때문에 "rubric을 몇 차례 테스트하며 보정"하는 작업 자체가 제약된다는 문제 제기가 있었음. 대응 방안:

- **UI/스트리밍 반복 확인**: 1차에서 이미 만들어둔 [`generate-practice-mock.ts`](../../src/features/prompt-builder/lib/generate-practice-mock.ts)를 재사용 — 실제 API 호출 없이 렌더링·상태 흐름을 반복 확인하는 용도로 이미 존재함.
- **rubric 개발/검증**: concept×difficulty 조합 10~15개 정도로 실제 API 응답을 **한 번만** 캡처해 파일(JSON)로 저장 → 이후 rubric 통과 여부는 저장된 샘플을 대상으로 로컬에서 반복 검증(API 호출 없음) → rubric이 안정되면 마지막에만 실제 API로 최종 확인.
