## 2. 파일 단위 의존성 분석

병렬 작업 가능 여부를 판단하기 위해 실제 코드를 확인한 결과, MVP 6개 항목 중 3개가 아래 3개 핵심 파일을 공유한다.

- `src/lib/llm/types.ts` — `practiceGenerationSchema` (LLM 응답 스키마)
- `src/features/prompt-builder/lib/build-prompt.ts` — `SYSTEM_PROMPT` (이미 기본적인 인젝션 방어 문구 포함, §27줄)
- `src/app/api/practice/route.ts` — API 핸들러(`streamObject` 호출부, try/catch)

| 항목 | 건드리는 파일 | 다른 항목과 겹침 |
|---|---|---|
| CI/CD 코드체크(lint/tsc) | `.github/workflows/*`, `package.json` | 없음 |
| 핵심 단위 테스트 | 신규 테스트 파일 위주 | 없음 |
| 재현성 + LLM rubric | 신규 스크립트/픽스처 파일 위주 | 없음 |
| 이상 입력 엣지케이스(개념 적합성 판별) | `types.ts`, `build-prompt.ts`, `route.ts`, UI | 인젝션 방어·실패처리와 겹침 |
| 프롬프트 인젝션 방어 | `build-prompt.ts`(`SYSTEM_PROMPT`) | 개념판별과 같은 문자열 수정 |
| 실패 처리·재시도 | `route.ts`, `generate-practice.ts` | 개념판별과 같은 try/catch 블록 수정 |

**결론**: 개념 적합성 판별·프롬프트 인젝션 방어·실패 처리·재시도 세 항목은 같은 파일, 심지어 같은 함수(`SYSTEM_PROMPT` 문자열, `route.ts`의 try/catch)를 동시에 고치게 되어 별도 워크트리로 병렬 진행 시 충돌이 거의 확실하다. 이 세 항목은 **한 워크트리에서 순차로** 진행한다.

## 3. 워크트리 분리안

```
main
 ├─ feat/ci-lint-check        (독립, 병렬 가능)
 ├─ feat/core-unit-tests      (독립, 병렬 가능)
 ├─ feat/rubric-reproducibility (독립, 병렬 가능)
 └─ feat/generation-safety    (순차 진행: 개념판별 → 인젝션방어 → 실패처리·재시도)
```

앞 3개는 서로 다른 세션에서 동시에 진행 가능. `feat/generation-safety`는 위 3개가 어느 정도 정리된 뒤, 혹은 병렬로 시작하되 세 하위 작업은 그 안에서 순서대로(개념판별 → 인젝션방어 → 실패처리) 진행한다.
