## Problem Statement

프론트엔드 개발 부트캠프 멘토링에서 관찰된 문제: 학습자는 VOD 강의를 보고 실습을 진행하지만, **배운 개념/이론을 실습이나 과제에 적용하는 걸 잘 못한다.**

1차 해결 시도(멘토가 AI 활용 학습법을 가이드하고, Gemini Gems에 지침을 복사해 활용할 수 있도록 안내)는 팀 4~5명 중 1~2명이 시도했고, 시도한 사람은 "현 수준에 맞는 실습 내용을 만들어낼 수 있었다"는 효과를 봤다. 그런데도 2주 안에 이탈했다. 이탈 원인은 세 가지였다:
- 어떻게 물어봐야 할지 모름 (프롬프트 장벽)
- 스스로 판단하기 부족한 부분이 있음 (자기평가 불가)
- 실습 지시를 받아도 에디터로 옮겨가는 절차가 번거로워 지속성이 떨어짐 (**전환 비용이 진짜 이탈 원인**)

## What Makes This Real

이건 가상의 아이디어가 아니라 이미 초기 검증이 있는 문제다:
- 실제 사용자 4~5명 중 1~2명이 시도했고, 시도자는 구체적 효용("현 수준에 맞는 실습 생성")을 직접 보고했다
- 실패 원인이 "AI 성능"이 아니라 "UI/전환 비용"이라는 것을 멘토링 현장에서 직접 관찰함
- 만드는 사람이 이 문제의 멘토 본인이며, 이미 방법론(PCM-L: Layered Competency Mentoring — 1단계 익숙해지기 / 2단계 연결하기 / 3단계 판단하기)을 직접 설계해뒀다. 챗봇이 실패한 진짜 이유는 프롬프트 장벽뿐 아니라 **AI가 학습자의 단계를 모르고 균일하게 반응**했기 때문이다.

## Target User

프론트엔드 개발을 이제 막 배우기 시작한 부트캠프 학습자. VOD 강의를 보고 개념은 알지만 실습에 적용하는 방법을 모르는 상태. 진입 트리거는 "막힌 지점"이 아니라 **"방금 이 개념을 배웠다"** — 즉 사후 트러블슈팅이 아니라 강의 직후 개념→적용 브릿지가 최우선 목표.

**진입 트리거가 "방금 배운 개념"이든 "막힌 지점"이든 관계없이, 핵심 장벽은 동일하다: 사용자는 AI에게 무엇을 어떻게 요청해야 할지 모른다.** 기존 Gemini 챗봇 실패의 1차 원인도 이것이었다. 따라서 이 프로젝트의 핵심 기능은 "AI가 실습을 잘 만든다"가 아니라 **"사용자가 프롬프트를 작성하지 않아도 되도록 입력 자체를 UI로 구조화한다"**이다. 자유 텍스트 입력창은 이 프로젝트에서 보조 수단일 뿐, 주 입력 메커니즘이 아니다.

## Full Vision — LXP 유저 플로우 (참고용, 이번 스코프 아님)

```
[1] 컨텍스트: 방금 학습한 개념/단원 입력 (+ 선택: 이전 세션 이력 자동 누적)
[2] 개인화된 실습 생성 ★ 이번 프로젝트 스코프
[3] 인앱 실행 (Sandpack) ★ 이번 프로젝트 스코프
[4] 실행결과+코드 기반 스트리밍 AI 피드백/힌트 ★ 이번 프로젝트 스코프 (P1)
[5] 반복 루프 (수정→재실행→피드백)
[6] 회고 기록 — "오늘 성장 지점" 축적 (미래 비전)
[7] 멘토 대시보드 — 멘티별 단계·막힌 지점·판단 패턴 한눈에 보기 (미래 비전, 비대면 1:n 운영 핵심)
```

이번 5일 프로젝트는 [1]~[4]를 화면 하나에 구현한다. [6]~[7]은 인증/데이터 저장/멘토용 화면이 필요해 5일 프론트엔드 화면 과제 범위를 넘으므로 Future Vision으로만 남긴다. 검증되지 않은 확장 후보(OOP/설계 트랙, 신규 개념 학습 트랙 등)는 Full Vision에 올리지 않고 `## Backlog` 섹션에서만 관리한다 — 실제로 필요한 사람이 있는지 확인된 뒤에 vision으로 승격한다.

## Constraints

- 부트캠프 1차 프로젝트 가이드 (AI NATIVE CAREER CAMP): 5일, 프론트엔드 개발 트랙 플래그십 — "AI 기능이 들어간 프로덕트 화면" (실시간 스트리밍 UI, 로딩/에러/빈화면 상태, 접근성, 반응형)
- 평가 배점: 문제정의15 / 동작완성도20 / 성능지표20 / 안정성15 / 재현성15 / 문서회고15
- 오늘(1일차) 예산: 4시간, PRD 제출까지
- 산출물: 동작 웹앱 + 컴포넌트 문서 + 성능·접근성 리포트 + 회고

## Premises

1. 진짜 문제는 "AI가 목함/난이도를 잘못 조절함"이 아니라 "사용자가 무엇을 물어야 할지 모르고, AI가 학습자 단계를 모르고 균일하게 반응한다"는 것 — 동의됨
2. 기존 Gemini 챗봇 방식의 실패 원인은 AI 성능이 아니라 **지시 생성 후 에디터로 옮겨가는 전환 비용**이었다 — 동의됨 (플로우 재설계로 반영: 실행이 같은 화면 안에 있어야 함)
3. 5일 안에는 화면 하나(개인화 실습 생성 + 인앱 실행 루프)만 만들고, 회고 기록·멘토 대시보드는 PRD에 미래 비전으로만 적는다 — 동의됨
4. 차별화 스토리는 "PCM-L(3단계 학습 프레임워크)을 직접 설계하고 제품화했다" — 동의됨

## Hypothesis & Validation Strategy

**가설:** 프롬프트 입력을 최소화하고(구조화된 선택 UI) 실습 환경(생성+실행+피드백)을 한 화면에 맞춤형으로 통합하면, 학습자가 실습 전환을 더 쉽게 지속할 수 있다.

**검증 전략:** 5일 안에 실사용자 행동 데이터(실제 이탈률 감소 등)를 구하는 건 불가능하므로, 기술·설계 차원의 대리 지표로 검증한다.
- 생성 품질 자가 채점: 개념×PCM-L 3단계 조합 샘플(예: 5개념×3단계=15건)을 체크리스트(정답 미제공 / 완료기준 명확성 / 실제 실행 가능성)로 직접 채점해 통과율 산출
- 전환 비용 정량 비교: 기존 방식(챗봇 직접 프롬프트 작성 + 외부 에디터 이동) vs 이번 방식(구조화 선택 + 같은 화면 실행)의 필요 클릭 수·화면 전환 횟수를 설계 비교표로 제시
- Lighthouse 성능/접근성, 번들 크기, 첫 상호작용 체감 시간의 스트리밍 UI 적용 전후 비교
- 이상 입력에서도 상태 처리가 깨지지 않는지, 동일 입력에 대한 재현성 확인

**한계:** 이 검증은 전부 기술·설계 차원이며 "실제 학습자의 지속률이 올랐는가"는 이번 스코프에서 증명하지 못한다. Open Questions/회고에 명시할 한계로 남긴다.

## 핵심 메커니즘: 구조화된 프롬프트 빌더 = 실습 생성 온보딩 (Structured Prompt Builder)

**명명 (2026-08-21 확정):** 이 4스텝 플로우를 "실습 생성 온보딩"으로 부른다. openlume 등 커리큘럼 온보딩 플로우와 이름을 맞추되, 스코프는 "이 실습 하나"로 한정한다(아래 백로그의 커리큘럼형 확장과는 구분).

사용자는 프롬프트를 직접 작성하지 않는다. 대신 아래 슬롯을 채우면 시스템이 내부적으로 LLM 프롬프트를 조립한다. 자유 텍스트는 마지막 슬롯 하나뿐이며 선택 사항이다.

1. **개념/기술명 입력** (자동완성 하이브리드) — 한 줄 자유 텍스트 입력 + 타이핑 중 자주 나오는 개념 목록(예: 20~30개, useEffect, 배열 메서드, 이벤트 버블링 등)이 자동완성으로 매칭 제안된다. 목록에 없는 개념도 그냥 직접 타이핑해서 제출 가능 — 폐쇄형 드롭다운이 아니다. **원칙 경계:** 이 필드는 "무엇을 배웠는지" 명사(짧은 개념/기술명)만 받는다. 지시문 조립(무엇을 해달라고 요청하는지)은 여전히 슬롯 2(상태 선택기)+슬롯 3(상황 칩)이 전담한다 — placeholder는 `"배운 기술/개념을 짧게 입력하세요 (예: useEffect, 이벤트 버블링)"`처럼 명사 입력을 유도하고, `"~실습을 만들어줘"` 같은 지시문 작성을 유도하지 않는다. (2026-08-20 CEO 리뷰에서 확정: 순수 자유텍스트는 원시 프롬프트 회귀 위험, 순수 고정 목록은 커버리지 문제 — 하이브리드로 절충)
2. **상태 선택기** (PCM-L 3단계, 카드형 단일 선택, 수치심 없는 선택지) —
   - A) 다시 설명 들으면 이해 가능 (1단계: 익숙해지기)
   - B) 혼자 적용해볼 수 있음 (2단계: 연결하기)
   - C) 다른 사람에게 설명 가능 (3단계: 판단하기)

   **카드 라벨 재검토 (2026-08-21, 결정 대기):** 초기 학습자에게 지금 어느 수준인지 한눈에 안 들어온다는 피드백 — 서술문(위 A/B/C)은 유지하되, 그 위에 짧은 단계명 라벨을 제목으로 얹는다. "전문가"류 등급명은 타깃(초기 학습자)과 거리가 있어 배제. 후보:
   - **익숙해지기 / 연결하기 / 판단하기** — 기존 PCM-L 단계명을 그대로 제목으로 승격(신규 용어 없음, 제품 고유 어휘 일관성 유지)
   - **다시 볼게요 / 해볼게요 / 설명할게요** — 사용자 1인칭 진행 상태로, 서술문 톤과 더 가깝게
3. **상황 칩** (멀티셀렉트 quick tag, 자유 서술 대체) —
   - "문법은 아는데 언제 쓰는지 모르겠어요"
   - "코드가 자꾸 에러나요"
   - "설명을 들어도 이해가 잘 안 가요"
   - "이미 아는데 연습만 더 하고 싶어요"

   **확장 검토:** 이 슬롯이 "어떤 지점으로 좁혀서 실습할지"를 결정하므로 목표 설정과 연결된다는 관찰 — 구체적인 확장 방향은 `## Backlog` 참조.
4. **(선택) 한 줄 자유 입력** — "더 구체적으로 알려줄 게 있다면" — 위 3개 슬롯으로 커버되지 않는 예외적 상황만을 위한 보조 입력. 이 필드가 비어 있어도 생성은 정상 동작해야 한다(필수값 아님).

내부적으로 이 4개 슬롯 → 서버(또는 클라이언트)에서 LLM 프롬프트 템플릿에 채워 넣어 호출한다. **수용 기준: 사용자가 원시 텍스트로 AI에게 요청을 "작성"하는 흐름이 어디에도 없어야 한다.** 이게 챗봇 복붙 방식과의 근본적 차이이며, 이번 프로젝트에서 가장 우선적으로 검증해야 할 UI 설계다.

## Approaches Considered

### Approach A: 실행 없는 텍스트/코드 정적 평가
사용자가 코드를 붙여넣으면 AI가 텍스트로만 평가·피드백. 실제 실행 없음.
- Effort: S / Risk: Low
- Reuses: 없음, 순수 LLM 호출
- Pros: 5일 내 가장 안전하게 완성, 상태처리·스트리밍·접근성에 집중 가능
- Cons: 사용자가 원한 "전환 비용 제거" 효과가 약함 — 실제 실행 검증 없이 코드만 보고 판단

### Approach B: 자체 Web Worker 샌드박스
Monaco/CodeMirror + Web Worker로 JS 스니펫을 직접 실행하는 자체 구현.
- Effort: L / Risk: Med-High
- Reuses: 없음, 전부 자체 구현
- Pros: 완전한 자체 구현이라는 포트폴리오 어필
- Cons: 5일 안에 샌드박스 보안·안정성까지 챙기기엔 리스크가 너무 큼. Scope creep 위험

### Approach C (선택): Sandpack(CodeSandbox SDK) 임베드 — 기본 에디터
이미 검증된 오픈소스 임베드 IDE(Sandpack)를 가져와 실제 코드 실행(React/JS, 브라우저 내, 서버 불필요)을 담보. 에디터는 Sandpack 기본값(CodeMirror 기반)을 그대로 쓰고, 실행 엔진과 AI 지시/피드백 패널은 독립 컴포넌트로 분리해 나중에 에디터만 Monaco로 교체 가능하게 구성.
- Effort: M / Risk: Med
- Reuses: `@codesandbox/sandpack-react` (검증된 오픈소스)
- Pros: 진짜 "실행-피드백 루프"를 5일 안에 안전하게 담보, 자체 샌드박스를 짜는 위험을 회피, AI 지시/피드백 패널이라는 실제 구현에 시간 집중 가능
- Cons: 외부 라이브러리 종속성, iframe 기반이라 Lighthouse 성능 점수에 영향 있음 (수용 기준에서 허용 범위 명시 필요)

## Recommended Approach

**Approach C: Sandpack 기본 에디터 + AI 지시/피드백 패널**

이유: 5일 예산에서 실행 엔진을 직접 만드는 것(B)은 리스크가 너무 크고, 실행이 없는 정적 평가(A)는 사용자가 관찰한 진짜 이탈 원인(전환 비용)을 해결하지 못한다. C는 검증된 실행 엔진 위에 진짜 차별점(PCM-L 기반 개인화 지시 생성 + 스트리밍 피드백)을 쌓을 수 있다.

**아키텍처 원칙 — 에디터 스왑 가능성은 이번 스코프에서 뺀다 (2026-08-20 SCOPE REDUCTION 리뷰에서 확정):**
`<PracticeEditor>` 어댑터 레이어는 만들지 않는다. Sandpack을 직접 사용한다. 이유: 5일 안에 실제로 Monaco로 교체하는 작업은 스코프에 없는데, 지금 당장 쓰이지 않을 추상화에 시간을 쓰는 건 과잉설계(YAGNI)이고, 그 시간은 스트리밍·상태 안정성처럼 실제 평가 배점(동작완성도20·안정성15)에 걸리는 곳에 써야 한다. 향후 LXP 플랫폼 타겟팅으로 실제 Monaco 교체가 필요해지는 시점에, 그때 가서 리팩터링한다.

**화면 구성 (단일 화면, 3개 영역) — 워크스루로 확정한 세부 동작 포함:**
1. **구조화된 프롬프트 빌더 영역** — 4개 슬롯(개념 선택기 / 상태 선택기 / 상황 칩 / 선택적 한 줄 입력). 생성 후에는 입력창이 사라지고 **선택 요약 칩**(예: `이벤트 버블링 · 연결하기 단계 · "언제 쓰는지 모르겠음"`)으로 화면 상단에 고정 표시 — 클릭하면 재선택 가능. 사용자는 원시 프롬프트를 절대 작성하지 않는다.
2. **Sandpack 에디터 + 실행 프리뷰 영역** — AI가 시작 코드를 스트리밍으로 채우는 동안 에디터는 **read-only**(스트리밍 중 사용자 타이핑과 충돌 방지). 스트리밍 완료 시 시각적으로 명확히 **editable로 전환**(테두리색 변화 등). 그 이후 `[실행]`은 자유롭게 여러 번 반복 가능.
3. **AI 지시/피드백 패널** — 지시는 생성 시 자동 스트리밍. 피드백은 `[코드 확인받기]`라는 **명시적 버튼**으로만 트리거(실행마다 자동 호출 안 함 — 비용·산만함 방지). 피드백은 정답을 바로 주지 않고 관찰 결과를 해석해주고 다음 예측 질문을 던지는 톤(PCM-L 멘토 질문 원칙과 동일).

**상태 관리:** 화면 전체 상태(입력값, 생성 상태: idle/streaming/error/done, Sandpack 코드 상태)는 최소 전역 상태 하나로 관리하고, Sandpack 내부 코드 상태는 Sandpack 자체 컨텍스트에 위임 — 상태를 이중으로 소유하지 않는다.

- **Sandpack 에러 오버레이 한글 mojibake (2026-08-25 추가)** — `/practice/[id]`에서 문법 오류가 있는 한글 주석 코드를 실행하면 "Something went wrong" 오버레이 안 한글 텍스트가 mojibake(예: "ìŠµë‹ˆë‹¤")로 깨짐. Windows Chrome에서 실제 확인됨(macOS 헤드리스 Chromium에서는 여러 방식으로 재현 시도했으나 재현 안 됨). 조사 결과 `@codesandbox/sandpack-react`의 `useErrorMessage()`는 `sandpack.error.message` 문자열을 가공 없이 그대로 노출하며, 이 문자열(코드 프레임 포함) 자체가 원격 CodeSandbox 번들러 서비스(`2-19-8-sandpack.codesandbox.io`의 Babel worker)가 만들어 `postMessage`로 전달하는 것이라 — 이 프로젝트의 `SandpackProvider`/`SandpackCodeEditor` 옵션으로는 손댈 수 없는 지점일 가능성이 높음. Windows에서만 재현되는 원인은 미규명. 방어적 워크어라운드(에러 텍스트가 전부 코드포인트 0xFF 이하일 때만 UTF-8로 재디코딩해 mojibake를 사후 복구하는 커스텀 오버레이)를 구현까지 해봤으나 미리보기 iframe 자체 에러 UI와 겹쳐 보이는 부작용이 있어 이번 스코프에서는 제외하고 보류. 다음에 다시 다룰 때는 Windows Chrome 네트워크 탭에서 실제 페이로드를 바이트 단위로 캡처해 원인을 좁히는 것부터 시작.

## Performance Comparison Methodology (2026-08-20 확정)

Lighthouse/번들 크기 "개선 전후 비교"는 **별도의 두 빌드(스트리밍 on/off)를 만들지 않는다.** 단일 빌드에서 개발 순서에 따라 순차 계측한다:
1. 스트리밍 적용 전(응답 완료 후 한 번에 렌더링하는 초기 버전)에서 1차 계측
2. 스트리밍 적용 후 동일 빌드에서 2차 계측
3. 첫 토큰까지 체감 시간(TTFT)은 코드로 직접 계측해 수치로 제시

이유: 평가 기준(성능 지표 20점)이 요구하는 건 "수치와 근거"이지 A/B 빌드 그 자체가 아니다. 별도 빌드 유지비용을 Day4의 이미 빠듯한 일정에 추가하지 않는다.
